# Admin Diagnostics

Lives in `easy-mcp-ai/includes/diagnostics/`. Answers "why can't my AI client connect?" from **inside** WordPress, where an external probe is blind: a missing table, a token whose filter chain yields zero tools, an `Authorization` header the web server drops before PHP runs. Spec and full history: `docs/plans/2026-08-04-admin-diagnostics.md`.

## Registering a check

`Diagnostics::register( callable $cb, string $id = '', bool $deep_only = false )` — `$cb` returns `Diagnostic_Result[]` and anything else is ignored; `$id` is a **fallback** id used only if `$cb` throws, so the report can still name which check could not run; `$deep_only` confines the check to an explicit Re-run, for costs that are unbounded on a page load (whole-table counts, per-site loops on a large network).

`Diagnostics::register_core_checks( $tool_registry = null )` wires every shipped check, one `register()` call per group. Two things there are load-bearing:

- **Group D receives the LIVE registry by handle**, not a fresh one. `Dynamic_Tool_Registrar` populates the plugin's own instance with third-party abilities; a registry built inside the check via `auto_discover()` holds static tools only, so D6 and D7 would report on a list that never contained a single ability. Passing the handle also means abilities registered later on `wp_loaded` are present by the time checks run on `admin_init`.
- **The five deep-only registrations are A1, A9, A10, Group H and Group I.** On a shallow run they do not vanish — they collapse to one "not run" placeholder each, which is why the suite yields **53 results on a deep run and 47 on a page load** — A1 and A11 share one probe request, so the deep total gained a result without gaining a registration.

**Result model.** Every check returns a `Diagnostic_Result` with one of 4 statuses (PASS/WARN/FAIL/UNKNOWN) and one of 3 tiers (blocker/warning/info). The value object is the single authority on routing: only **blocker + FAIL** raises the admin banner, blocker|warning reach Site Health, everything reaches the dashboard card. UNKNOWN never renders as a problem.

**Execution.** No cron, ever — B3 exists because cron may itself be broken. The suite runs only when an admin is looking: a plugin-admin page load with a report older than 24h, or a nonce-checked Re-run (which is also the only path that runs the deep-only work — **5 registrations yielding 11 results**: A1's loopback probe which also carries A11, A9's edge-block probe which also carries A12, A10's root-discovery probe, Group H's four table counts, Group I's two per-site checks). `Diagnostics::maybe_run()` requires `manage_options`: `wp-admin/admin-post.php` fires `admin_init` **before** its logged-in check, so a screen gate alone let anonymous requests drive the suite. The report caches in a **non-autoloaded option, never a transient** — B1 exists precisely because transients cannot be trusted on the sites this diagnoses.

**Writing or changing a check — the rules that matter** (§3.1; each was learned from a shipped defect):

| Rule | The trap |
|---|---|
| 1. Detection ≠ causation | A deliberate admin choice is never a warning |
| 2. UNKNOWN over guessing | "I could not look" is not "it is fine" |
| 3. Blockers must be deterministic | Banners only for directly observed hard failures |
| 4. Web-server awareness | Skip, don't UNKNOWN, what does not apply |
| 5. **PASS means measured** | Applies to the DATA SOURCE, not just the wiring. A guard that makes a reader *safe* does not make it *honest*. Violated 15 times |
| 6. Labels name the healthy property | "Tool categories fully disabled — Pass" contradicts itself. **Corollary:** any surface that lists a problem without a Pass/Warn/Fail column beside it must prefix `Diagnostic_Result::problem_badge_html()`, or a list of problems reads as a list of reassurances |
| 7. **Measure what a real request sees** | Not the value this request already repaired, inflated or defaulted. Found 7 separate instances |

Rule 7 is the one that keeps recurring. B1 measured a per-request cache array its own write had just filled; G2 read `memory_limit` after wp-admin raised it to 256M; D1 defaulted a corrupt allowlist to `['*']` where production uses `[]`. Each had passing unit tests, because the tests supplied inputs the production reader never fetched. **Review the reader and the evaluator separately**, and for any check whose evaluator takes collected data, write the "collection returned nothing" test explicitly.

**Verifying a change.** Unit tests alone are not sufficient for this subsystem — see `tests/docker/object-cache/`, which runs the real Redis Object Cache drop-in and stops the container, because the earlier harness used a stub with no runtime cache and therefore certified a check that did not work. `./tests/docker/run-all.sh` runs every harness.

**A5 is a heuristic with stated limits, and it lexes rather than samples.** The stray-output check reads the whole of `wp-config.php` and the active theme's `functions.php` through `token_get_all()` and counts inline HTML at brace depth ZERO. It used to read the last 64 bytes and scan back for `?>`; round 3 widened that to 64 KB so a large amount of trailing junk could still be seen, and in doing so made the check WARN on healthy files — a `?>` inside a hook callback, a string literal or a comment now fell inside the window and read as the end of PHP (round-4 R4DG001, a regression from R3DG001's own fix). Whether a `?>` ends PHP mode is not decidable from the end of a file. Two details are load-bearing: inline HTML inside a function or conditional body is emitted only when that body RUNS, and nothing runs at include time; and `T_CURLY_OPEN`/`T_DOLLAR_OPEN_CURLY_BRACES` are the `{` of a `"{$x}"` interpolation, so a depth counter that skips them reads the inline HTML that follows as top-level output — measured, 29 bytes reported where PHP emits 0. `token_get_all()` is called without `TOKEN_PARSE` so newer syntax lexes instead of throwing, and lexing is skipped entirely when the source contains no `?>` — airtight, because inline HTML after index 0 requires one, and it keeps whole-file lexing (~28× the file size in peak memory, an UNCATCHABLE fatal if it blows) off 17 of 34 real themes. **Two limits are deliberate and recorded** (round-5 R5DG001/R5DG002): a top-level braced body that DOES run emits its HTML and is reported clean, and top-level alternative syntax (`if: … endif;`) and `goto` are counted as emitted when they may not be. The obvious depth tracker for the second was implemented and measured — an `if: elseif: else: endif;` chain opens three times and closes once, so on a fixture emitting 28 bytes it reported 0 and PASSED, turning a false WARN into a false PASS. A 65-theme scan found zero real false positives, because the idiom is always inside a function body. **Do not attempt a fifth rewrite of this check without measuring against real emission first.**

**Ask what would fail if the guard were deleted.** Two adversarial audits (spec §13, §14) found the same pattern twice, and neither time was it in the check logic: §13's only HIGH existed because a stub drop-in could not exhibit the fault it was built to prove, and §14's largest finding was a security gate — `Check_Multisite::may_read_network()` — that could be deleted outright with all 2413 tests staying green, because `is_multisite()` was hardcoded `false` in the stubs and the gate was never reached. When you add a guard here, mutate it and run the suite; if nothing fails, the guard is decoration. `is_multisite()`, `is_super_admin()` and `wp_cache_supports()` are now stub-controllable for exactly this reason.

**Two audits, two near-misses.** In both rounds the single most promising finding would have caused a regression if acted on directly — most recently a proposal to gate B1's `wp_cache_flush_runtime()` on `wp_using_ext_object_cache()`, which would have reintroduced the C1 false PASS on every site without a drop-in, because `get_transient()` reads `wp_cache_get()` before touching MySQL. Verify findings against real core source before changing anything.

**A9 is the only check whose subject is outside PHP, and it works by differential.** A CDN or WAF rule that blocks the AI client's user agent refuses the request *before* WordPress runs, so the audit log, the change log and any request logging inside the site all show the same thing — a flawless OAuth handshake followed by silence — while the client reports only "Authorization with the MCP server failed". Measured 2026-08-11: the claude.ai connector performs discovery, DCR and the token exchange with a generic HTTP client, then sends **every** MCP call (`initialize`, `tools/list`, `tools/call`) as `User-Agent: Claude-User`; a Cloudflare AI-bot rule answered that agent `403 Your request was blocked.` while answering the plugin's own agent with the ordinary 401 challenge. A9 therefore sends the same unauthenticated GET to its own MCP URL twice, differing only in `User-Agent`, and compares. **The differential is the measurement** — a 403 alone could be a firewalled loopback or a captive portal, so the control must come back as OUR 401 carrying the `resource_metadata` challenge built from this site's `home_url` (A1's constraint 2, restated) or the verdict is UNKNOWN. Three stated limits, deliberately not engineered away: PASS means "no user-agent block detected", never "Claude can reach this site" (an IP/ASN block still lets the probe through, since it leaves from the origin's own address); a host that resolves its own domain locally never crosses the edge and will PASS while a real client is blocked; and the agent strings are a maintained heuristic, not a specification. Each guard was mutated and the suite fails — see `DiagnosticsEdgeBlockTest`. **The REMEDIATION is leg-aware, and that was learned the hard way.** It pointed every owner at Cloudflare's "AI bot / AI Scrapers and Crawlers" option until 2026-08-25, when a measured case had no CDN at all: plain nginx refusing any user agent beginning `python-`, so `python-httpx` and `python-requests` got connection resets while `httpx/1.0`, `aiohttp`, `Claude-User` and `curl` all returned 200. The blocked set was the HANDSHAKE leg alone. A9 detected it correctly and then gave advice for a setting the owner did not have — **correct and unactionable, and the report records it having been read as noise.** `blocked_fix()` now branches the same way `blocked_detail()` always did: the MCP leg is refused by AI-bot rule sets naming Claude, the handshake leg by generic rules matching HTTP client libraries, which live in nginx and Apache config, ModSecurity rule sets and security plugins as often as in a CDN. **Where one edge rule exists, look for the other** — that site also blocked the whole `/.well-known/` prefix, and fixing only one would have left the connector equally broken.

**A10 is A9's sibling, and answers the question A9 cannot.** A9 asks whether the client's NAME gets through; A10 asks whether the two documents it must read *before* it has any credential get through at all. Some managed hosts answer the whole `/.well-known/` prefix themselves and never pass it to PHP — measured 2026-08-21 on SiteGround, where `oauth-protected-resource`, `oauth-authorization-server`, `acme-challenge` and names invented on the spot all returned the host's own static 404, while `/wp-json/` reached PHP normally and the MCP endpoint answered its 401 correctly. Nothing inside WordPress could see it: the plugin was active, the routes registered, every other check green, and the connector still impossible to create. RFC 8414 and RFC 9728 both insert the well-known segment between host and path, so no choice of issuer moves those URLs out of that prefix — **the plugin cannot relocate them; only the host can open the path.** Like A9 it works by differential: the same document is served on a REST-path mirror under `/wp-json/`, so if the mirror returns our document and the root does not, that is an observed refusal in front of PHP on this host in this second. A root failure ALONE proves nothing — a firewalled loopback answers identically — so the mirror is the control and without it the verdict is UNKNOWN. Three guards, each mutated and each failing the suite when removed (`DiagnosticsDiscoveryTest`): the control gate, a DECODE gate that stops a "soft 404" (HTTP 200 carrying an HTML error page) reading as healthy — it is `json_decode`, **not** a content-type check, and that distinction is deliberate, because the documented workaround puts these documents in the webroot as extensionless files that some servers serve as `text/plain`; requiring `application/json` would fail a setup that genuinely works — and an origin marker requiring the body to name this site. Same stated limit as A9: a host that resolves its own domain locally never crosses the edge and will PASS while a real client is blocked. **A10 also answers a second question**, because the documented fix for a blocked host is a static file and a static file does not update itself: each root is compared against ITS OWN mirror, which the same `Discovery` method builds (`handle_well_known()` delegates to it, so the two are identical by construction on a healthy site — verified live, the comparison does not false-alarm). A difference means the root has drifted; drift in `SIGN_IN_FIELDS` is a **blocker**, drift anywhere else is a **warning**, because the connector still works and only the offered permissions are stale. Note the split between `looks_like_our_document()` (shape: it decodes and carries `resource` or `issuer`) and `is_our_document()` (shape AND names this site). The root is classified by SHAPE and the origin proof lives in the control, exactly as A9 divides it — judged by the strict test, the likeliest real staleness case, a copy written before the site address changed, reads as "the host is answering for us", which is the wrong diagnosis and sends the owner to their host for something they can fix in a minute. Mutating that split fails the suite. **A10's control moved OFF `.well-known` on 2026-08-25, and the reason is the whole finding.** A second host was measured that refuses `.well-known` **anywhere in the path**, not as a root prefix — so `/wp-json/easy-mcp-ai/v1/.well-known/...` was refused exactly like the root, while plain `/wp-json/` returned 200 with a PHP header. That broke three things at once: A10 lost its control (`$measured` stayed 0, and the check told the owner their site could not call its own address, which was false), the owner lost the copy source the documented fix depends on, and the identification test in `docs/HOST-BLOCKS-WELL-KNOWN.md` inverted because neither URL answered. The control now lives at `/wp-json/easy-mcp-ai/v1/discovery/...`, which contains no `.well-known` segment and therefore survives both host shapes; the old mirrors stay registered so earlier instructions keep working. `OAuthDiscoveryMirrorTest` pins that the control path contains no `.well-known`, and mutating it back fails the suite. **The general rule: a control must not contain the string the fault matches on.** **The REST mirrors exist for A10 and for the owner** — on a blocked host the only route back is to place the documents in the webroot by hand, and they need somewhere to read them from; they are deliberately unadvertised, so no client can discover them as a second canonical URL (`OAuthDiscoveryMirrorTest`).

**A11 rides A1's request, and asks the question A1 never did.** Transport reads five request headers, and A1 probed one. `Mcp-Session-Id` is read at five points and is what holds a session together; `Mcp-Protocol-Version` selects the negotiated spec. A proxy that drops either leaves the plugin, the logs and every other check looking healthy while sessions silently fail — and A1 reported PASS throughout, because it only ever asked about `Authorization`. Both now travel on the SAME probe request, so the cost is zero extra round trips, and `run()` returns two results rather than one: different subjects need different labels (§3.1 rule 6), and one merged verdict would hide a working sign-in behind a broken session or the reverse. A11 inherits both of A1's binding constraints — **WARNING tier, never a blocker**, because the probe proves the PROBE's path and a real client's may differ; and **UNKNOWN without proof of origin**. Values derive from the one-shot secret so both sides compute them without a second round trip and a REWRITTEN header is caught, not merely a stripped one. `Origin` and `Accept` are deliberately not probed: we set `Origin` ourselves so it would test nothing, and we refuse SSE, so `Accept` negotiation barely matters. Guards mutated in `DiagnosticsHeaderProbeTest`: the value comparison, the proof gate, the absent-field gate and the case-insensitive name match all fail the suite when removed. **Live status: both verdicts OBSERVED against a real proxy.** `tests/docker/transport-edge/` runs nginx with `proxy_set_header Mcp-Session-Id "";` on :8086 and asserts `a11=WARN` there beside `a11=PASS` on the clean leg — both rows confirmed on `ubuntu-latest` in CI, 2026-08-25. The earlier note here said the WARN path was "covered by unit tests and mutation only", which was true of the SANDBOX attempt (`RequestHeader unset` under `.htaccess` never took effect on that stack) and was left standing after the harness closed it. A stale limitation reads as an open gap and gets re-investigated; if you close one, strike the sentence that described it.

**A12 is the only outbound check that uses the method the protocol runs on.** Every other one sends a GET; the MCP endpoint is registered POST-only and every tool call is a POST carrying JSON, so a rule rejecting POSTs or JSON bodies was invisible to the entire suite — A9 and A10 both PASS on a site where no client can make a single call. It rides A9's probe set (the GET control is already ours, so the path, host and TLS are known good) and adds one POST, making the METHOD the only variable. **Its stated limit is load-bearing and must not be engineered away**: the body is a minimal, ordinary `initialize`, and it deliberately does NOT probe with code- or SQL-shaped content, which is what managed WAF rules actually key on. A plugin firing attack-shaped payloads at its own site trips the site's own security plugin, can get the origin IP banned, and is precisely the behaviour that gets a plugin flagged. **One further cell is uncovered and worth naming**: A12's POST only ever carries the neutral plugin agent, and A9's agent probes only ever send GET, so an edge rule keyed on agent AND method together — refuse a POST from Claude-User — passes both checks. Neither is wrong; the pair simply does not cross those axes. So a PASS means "POST and JSON are accepted", never "your WAF will accept a real edit" — the WPVibe-documented case of writes containing code being blocked while reads pass remains outside what we can safely detect. **A12 and A9 treat a no-reply differently, and that is deliberate.** A9 has several agent probes and reads a single silent one as a possible network blip — WARN, never a banner, per rule 3. A12 sends exactly ONE request, so it has no second opinion: a POST that gets no answer beside a control that did is the only signal it has, and it fails at blocker tier. The cost is that a transient timeout on that single POST can raise the banner. That trade was accepted because the fault A12 exists for — an edge refusing the method every tool call uses — makes the site unusable while every other check stays green, and a missed blocker there is worse than an occasional false one. Recorded 2026-08-24; the divergence was pinned by test but written down nowhere, so it read as an inconsistency.

**A11 and A12 are proved by `tests/docker/transport-edge/`, not by unit tests.** Both faults live between the internet and PHP, so a real proxy has to really mangle a real request; nginx shares WordPress's namespace so the plugin's loopback crosses it. Stripping `Mcp-Session-Id` moves A11 to WARN and leaves A1 PASS; refusing POST moves A12 to FAIL and leaves A9 PASS. Forcing the A11 case on a managed sandbox failed first — `RequestHeader unset` had no effect there, and the first attempt was a silent no-op because `mod_headers` was absent and `<IfModule>` swallowed it, which made A11's PASS at that moment correct and nearly read as the check being blind.

**Two stubs were missing and hid a whole collection path.** `wp_remote_retrieve_header()` was never stubbed, so `Check_Edge_Block::run()` threw on the undefined function and every test calling it silently exercised the catch — A9's probe side was never once executed by a test, while its evaluator was, which is why nothing looked wrong. `wp_remote_post()` was absent for the same reason. Both are now in `tests/stubs/wordpress-stubs.php`. When a run() here returns fewer results than it should, suspect a missing stub before suspecting the code.

**What the audit log records, and why H1 is unaffected by the 2026-08-23 change.** It writes `success`, `error` (the tool ran and failed), `auth_failure` (the value **H1 counts**), and since 2026-08-23 `refused` — a call rejected BEFORE dispatch by any of six gates: the token allowlist (two branches, and the commonest of the lot), unknown tool, capability, disabled tool, or pattern filter. Before that, `log_tool_call()` sat after those gates and a refused call wrote nothing, which is exactly what an edge block also writes: the two were indistinguishable, defeating the cheapest triage step there is ("reproduce it, then see whether a row appeared"). **`refused` is deliberately not `auth_failure`** — reusing that value would make every disabled-tool call register as a sign-in attack and inflate H1. **Rate-limited calls are still not logged**, and that is a decision, not an omission: a row per rejected request grows the log fastest at the one moment it should stay small. **The refusal log is bounded by its OWN counter, not by the request limiter** — `Server::log_refusal()` counts ROWS WRITTEN per token per minute, at the same ceiling as the rate limit. Bounding it the other way was tried and reverted: moving `check_rate_limit()` above the allowlist gates put every refusal behind the limiter, but it also made a refused call SPEND the caller's budget, where on main it returned before the limiter and cost nothing. Measured live 2026-08-25 — limit 5, five refused calls, and the token's next LEGITIMATE call came back `RATE_LIMITED`. The realistic trigger is an allowlist narrowed after a client connected, so it still holds a stale `tools/list`, tries a tool that is now off-limits, and locks itself out of the tools it may still use. **Hitting the log ceiling stops the writing, never the answering** — the refusal is still returned. Both properties are pinned and both mutations fail the suite. Expect H4's row count to rise on sites that refuse calls routinely. Pinned by `ServerRefusalAuditTest`, including the rate-limit exclusion and the H1 collision.

**E6 exists because the consent screen is a FRONT-END page.** `?easy_mcp_ai_oauth=authorize` is served from the front of the site, not from wp-admin and not from `/wp-json/`, so a coming-soon or maintenance plugin can stand between an AI client and the only screen a connection cannot complete without. On the site that prompted A10 exactly that happened — the front end returned 500 because the theme's Coming Soon mode was on — and the HOST diagnosed it, because nothing in this suite looked at the front end at all. It reports at **INFO tier and never warns**, on E2's pattern: a holding page is a deliberate admin choice, and §3.1 rule 1 forbids treating one as a fault. E2 and E5 were each re-tiered to INFO after precisely that mistake reached the field; E6 starts there. **Measuring it directly was rejected, not overlooked**: probing the authorize URL would write an `auth_failure` row on every logged-out hit via `log_authorize_failure()`, and H1 counts exactly those — the check would manufacture evidence for another check, on data the owner reads (`docs/plans/2026-08-23-diagnostic-gap-analysis.md` §6.2). It is also the first always-on addition of this branch, so it moves the SHALLOW count as well as the deep one.

**Pin a tier POSITIVELY, or you have pinned nothing.** A mutation sweep on 2026-08-24 demoted every load-bearing tier in the suite to INFO one at a time and ran the full suite against each: **29 of 51 survived**. The branches were not untested — they were tested with assertions that cannot fail. `assertFalse( $r->renders_in_notice() )` is satisfied at info tier, because `renders_in_notice()` requires blocker **and** FAIL; so is `assertNotSame( TIER_BLOCKER, $r->tier() )`. The assertions that bite are `assertTrue( $r->renders_in_site_health() )` (false at info) and `assertSame( TIER_WARNING, $r->tier() )`. Group G caught 5 of its 6 only because it happened to assert the positive form. Tier is not decoration: it alone decides whether the admin banner fires and whether a check reaches Site Health, and the one unpinned BLOCKER was A8's proxy branch — the Cloudflare Flexible SSL case, on the check re-evaluated live on every render precisely because it is the only signal that owner gets. Each check class now carries one `test_every_warning_branch_keeps_its_site_health_routing()` sweep; add new branches to it. **And when you add a test here, prove it RUNS and prove it can FAIL** — two of these test files end with a fixture class, so a method appended before the file's last brace lands inside *that* class and PHPUnit silently runs nothing (measured: 34 tests before, 34 after, suite green, meaning nothing). See `docs/plans/2026-08-24-diagnostics-coverage-audit.md` for that run, and `docs/MUTATION-TESTING.md` for how to run one without fooling yourself.

**Surfaces:** `Diagnostics_Notices` (one aggregated banner, plugin screens only; A7/A8 are re-evaluated live on every render, not read from the cache), `Diagnostics_Site_Health` (Status tests + the copyable Info panel — fields default to `private`, see `COPY_SAFE_IDS`, because that panel is pasted into public forums and carried usernames and token names), and the dashboard card. Three of these list problems as `label — detail` with no status column, so all three prefix the severity badge from `Diagnostic_Result::problem_badge_html()` — the card's issue list, the banner and the Site Health group body. The word, the colour and the escaping live in the value object precisely so a fourth surface cannot ship a fourth spelling; the card's full results table and the copyable block already carry their own status column and do not use it.

**The live A7/A8 path needs its own isolation boundary.** `Diagnostics_Notices::current_blockers()` re-evaluates A7/A8 on every render (§7.1), and it called `Check_Notices::run()` with no `try`/`catch` while `Diagnostics::run()` wrapped every check in exactly that boundary a hundred lines away — so a throw took the plugin's admin screens down instead of degrading one banner. The throw surface is ordinary: `permalinks_are_plain()` reads `option_permalink_structure`, `oauth_transport_problem()` reads `home_url()`/`is_ssl()`, and `home_url` is filtered as a matter of course by multilingual, CDN and staging plugins. `live_results()` now catches `Throwable` **and** rejects a non-array return (a filter can break this by returning the wrong type without throwing, and `foreach` over a non-iterable is itself a fatal on PHP 8). On failure it falls through to the **cached** a7/a8 verdict, not to "no blockers" — that verdict was really measured, only possibly stale, and it still warns an admin whose permalinks are broken. Its `$runner` parameter exists so the catch is reachable from a test; anything unreachable is decoration.

**Gate reading, not just collecting.** `Check_Multisite::may_read_network()` stops a sub-site admin *running* I1, but the report is cached in `wp_N_options` (`get_option()` is per-site), so a super admin who views a plugin page **while on a sub-site** leaves sibling domains in that site's own options — where its administrator renders them. Reproduced on a 32-site network: the dashboard card emitted them to a non-super-admin. `Diagnostics::cached()` is the single choke point every surface reads through, so the redaction lives there and swaps I1 for the same "not permitted" UNKNOWN the collection gate returns; `class-check-multisite.php` loads only under `is_multisite()`, so single sites pay nothing. **It is applied on the way out and never written back into `self::$results`** — poisoning that memo would blank the report for a super admin whose own `run()` filled it in the same request, which is why a test reads twice and then switches user. Same lesson as the §13/§14 audits: when adding a guard here, mutate it and run the suite.

**Options:** `easy_mcp_ai_diagnostics_last_run` (cached report, non-autoloaded) and `easy_mcp_ai_header_probe_secret` (one-shot, arms A1's public probe route for one request). Both are purged on uninstall.
